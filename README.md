# Orbit

Version: 0.21.1 (see [CHANGELOG](CHANGELOG.md)).

## Why Orbit
Orbit gives one person working with Claude Code the habits of a small, careful software team.
- **A team, not a single assistant**: an explorer, a designer, a tech lead, a security officer, a coder and a reviewer each do one job, so every change is thought through, built, then checked by someone fresh.
- **Decisions made the way good teams make them**: `/decide` sizes the process to the question and starts on its own when a question needs it. A small fix just gets done; anything touching security or hard-to-undo choices gets proposals, a security review and a sign-off, with a written record of why. Critics loop a fixed number of times, then escalate: prefer a script as the critic (proof-check, intent-plan, audit-ledger), one LLM fix round (DEC-14), one Contest rebuttal (DEC-13); never loop until a critic is satisfied.
- **Parallel work without session upkeep**: one operator coordinates and never edits; every chore runs in a fresh worker subagent on its own branch (or in a peer session you can watch), work stays in flight, the operator resumes on its own after a compaction or restart, and nothing reaches the shared branch without passing its checks.
- **Lower cost**: cheaper models do the reading and routine building, and the strongest models are kept for judgment. Sessions message each other only when a decision is needed.
- **Big goals planned before they are built**: the `intent` skill (AI-DLC's Inception step) asks one round of questions, writes a milestone plan of small units with proofs as an OKF doc, checks it with a script, and waits for one approval before any issue or build.
- **Docs that stay small and current**: optional checks keep project docs short, indexed and updated alongside the code.
- **Works in any project**: everything specific to a project lives in one profile file.

## Contents in brief
Personal Claude Code plugin: six role agents (`explorer`, `designer`, `architect`, `security`, `coder`, `reviewer`, which also checks a fix round when its brief starts with `Mode: fix-round`), an `operator` main-session agent, the `/decide` PM command, the owner's `/orbit:unattended` go for merges while away, two skills for coordinating parallel work (`operator`, `peer`), the `intent` skill that plans a big goal as a milestone of small units, and the `okf` docs skill. Projects may opt in to pull requests per topic branch (`Pull requests: yes` in the profile); the merge stays a verified local `--no-ff` merge. A fresh worker starts every task; a worker is resumed only for its own open branch (profile `Worker reuse: fresh-per-task`, default; `resume-ok` opts out). Everything project-specific lives in a per-project profile.

## Install
Clone it once (the templates used in "Adopt in a project" come from the clone):
```
git clone https://github.com/Scrollout/orbit.git ~/orbit
```
Then, in Claude Code:
```
/plugin marketplace add ~/orbit
/plugin install orbit@scrollout
```
Agents appear as `orbit:<name>`, the command as `/orbit:decide`. The model starts `/orbit:decide` and the `intent` skill by itself when a question or goal needs them (it says why in one line), never inside a worker or subagent executing a brief; you can still type either.

**Update** to a new [release](https://github.com/Scrollout/orbit/releases):
```
git -C ~/orbit pull
```
then `/plugin marketplace update scrollout` and `/plugin update orbit@scrollout` in Claude Code, then `/reload-plugins` in each running session (or restart it; a running session keeps the definitions it loaded).

## Adopt in a project
1. `mkdir -p .agents && cp ~/orbit/templates/project.md .agents/project.md` and fill it in (TODO for unknowns). See `templates/project.example.md` for a filled one.
2. Optionally `cp templates/principles.md .agents/principles.md` and `templates/AGENTS.md ./AGENTS.md`.
3. Point `CLAUDE.md` or `AGENTS.md` at it: `@.agents/project.md` and `@.agents/principles.md` (Claude Code imports with `@` lines). If the profile lives elsewhere, state its path there; agents read `.agents/project.md` or that path first.
4. To run the main checkout's session as the operator: `cp ~/orbit/templates/operator.md .agents/operator.md` and `echo .agents/operator.md >> .git/info/exclude` (it stays untracked). Its SessionStart hook then hands that file (only while untracked and git-ignored, capped at 8000 bytes, git 2.31+; silent on older git) to the main checkout's session at startup, resume, clear and compaction, so the operator resumes without being told, with one line of the tracker features on (Tracker); sibling worktrees get nothing. Or start it directly as the operator with `claude --agent orbit:operator`.

## Contents
- `agents/`, `commands/decide.md`: the team and its process; models: architect and security on fable, reviewer on opus (sonnet for a tests-or-docs-only fix round), the rest on sonnet.
- `skills/intent`: plans a goal too big for one session as an approved milestone of small units (see Intent below).
- `skills/operator`, `skills/peer`: coordinating per-task worker subagents or peer sessions (push queue, merge protocol, auto-compaction, no manual `/clear` or `/compact`).
- `refs/decide/`, `skills/operator/refs/`: detail (tables, templates, per-step procedures) split out of the two long files; each core file keeps the numbered rules and the flow and says when to load each ref.
- `scripts/`, `rules/`, `skills/MANIFEST.json`: the drift guard (see Drift guard below).
- `hooks/operator-context.sh`: the operator's SessionStart hook (self-test: `sh hooks/operator-context.test.sh`).
- `hooks/guard.mjs`: the PreToolUse guard for OPR-01, DEC-08 and outward actions (see Operator guard and Outward guard below; tests: `scripts/guard.test.mjs`, `scripts/outward.test.mjs`). Threat model: [docs/threat-model.md](docs/threat-model.md).
- `commands/unattended.md`, `hooks/unattended.mjs`, `hooks/go.mjs`: the unattended go (see Unattended go below; tests: `scripts/unattended.test.mjs`).
- `templates/`: `project.md`, `project.example.md`, `operator.md`, `handoff.md`, `principles.md`, `AGENTS.md`.

## Drift guard
Keeps the skills and the sessions from drifting. Zero dependencies (Node built-ins, Node 20+); `npm test` runs every test and check below plus the hook self-test. Commands and skills call the scripts as `node "${CLAUDE_PLUGIN_ROOT}/scripts/<name>.mjs"` (scripts are plugin files, so always the plugin root; a skill's own refs use `${CLAUDE_SKILL_DIR}`); from a shell, run `node <orbit clone>/scripts/<name>.mjs`. Known limit: that variable expansion follows the official Claude Code docs but has not been verified live here.

### Layout and rules
- **Rule ids.** `/decide` (`DEC-01..`) and the `operator` skill (`OPR-01..`) each carry a numbered rule list, every rule tagged `script` (an orbit script checks it), `hook` (a hook enforces it: `enforced_by` in `rules/rules.json` names it, and a test checks the hook names the rule) or `judgment`. The prose and the refs explain the rules; the ids are stable. `rules/rules.json` registers them; a test checks each id appears once in its core and nowhere in a ref.
- **Core plus refs.** A file over 10000 characters (about 2500 tokens) or 100 lines is split: the core keeps the rules and the flow, `refs/decide/` and `skills/operator/refs/` hold detail, loaded when the core's "load when" line says so. Pointers use `${CLAUDE_PLUGIN_ROOT}` (commands) and `${CLAUDE_SKILL_DIR}` (skills), which Claude Code substitutes; a test resolves every one. `node scripts/check-size.mjs` fails over the threshold and lists the largest files.
- **Versions.** Each command and skill has `version:` in its frontmatter. `skills/MANIFEST.json` records version and a content hash for each core plus its refs, and one shared entry for `rules/*.json` and the scripts (versioned by `version` in `rules/rules.json`). `node scripts/manifest.mjs --check` fails on an edit without a version bump; after bumping, `--update` rewrites the manifest (it refuses an unbumped edit); `--print` lists hashes. Claude Code ignores unknown frontmatter keys. On other surfaces (claude.ai upload, the Skills API) unknown keys may be rejected: there the manifest is the source of truth, and the `version:` line can be stripped.
- **Docs.** `node scripts/check-docs.mjs` checks that plugin.json, the CHANGELOG and the `Version:` line above agree and that links and referenced paths resolve.
- **Plugin compliance** (#17, #18, #23). `scripts/plugin-meta.test.mjs` (in `npm test`, so `make quality`) checks what claude.ai and Claude Code reject: plugin.json keys documented, kebab-case name, SemVer version equal to the CHANGELOG top entry (and the marketplace entry's, if set), `author.name` and `license`; marketplace.json names the plugin with source `./`; descriptions at most 500 characters; frontmatter parses as YAML, holds only the documented keys of its kind (plus `version`), a documented `model`, and a skill's `name` equals its directory; hooks.json has documented events, `command` handlers, positive integer timeouts, a double-quoted `${CLAUDE_PLUGIN_ROOT}` and existing scripts; tracked files are at most 512, each at most 256 KiB, no symlinks, Windows-reserved names, colons, trailing dots or spaces or case-only collisions, with README.md and LICENSE. Each check has a planted-bad case. `make plugin-validate` (also in `make vet`) runs `claude plugin validate` on `.` and `.claude-plugin/plugin.json` from the toolbox's pinned Claude Code, offline and without auth; any warning but the one for `CLAUDE.md` at the root fails.

### Project profile block
`templates/project.md` ends with a fenced code block whose info string is `yaml orbit-profile`: `base_branch`, `security_paths` (an empty, `/` or `./` entry is a gap, never a match-all; globs anchored at the repo root: `*`, `**`, `**/Makefile` for any depth, a trailing `/` for a directory; no braces), `review_trailer`, `labels`, `issue_tracker`, `base_pusher` (`agent` or `owner`; the legacy `operator` reads as `agent` with a warning), `ci_policy` (`ci-only` or `local-full`) and optional `production_env`, optional `standing_waivers` (review-waived classes such as `docs-only`; `merge_built.waived` must cite one or be `owner` with a reason) optional `ledger_path` (default `.agents/ledger.jsonl`, untracked), optional `protected_branches` and `required_checks` (add-only; see Outward guard and Unattended go), and the optional release fields (see Releases): `release_when` (`change-set`, `milestone` or `never`), `release_via` (`ci` or `session`), `release_tool` (`none`, `release-please`, `changesets`, `semantic-release`, `goreleaser`, `other`), `changelog` and `version_files`; triage ignores them; optional `tdd` (`no` default, `yes`: DEC-21 and DEC-22 apply, or `auto`: decided per step at triage by `tdd-suggest.mjs`; `decide-triage.mjs` prints `tdd: yes|no` for the triage event; an invalid value such as `true` or `Yes` is a profile gap), `targeted_test` (the targeted-test command; required with `tdd: yes` or `auto`), optional `test_first_commit` (`no` default, or `yes` with `tdd: yes`: the coder commits the failing test alone before the fix, DEC-21; `profile.mjs` warns when it is yes without `tdd: yes`; triage ignores it); the optional tracker fields (see Tracker): `milestones` and `issue_types` (`yes` or `no`), `github_projects` (`off` default, or `on`), `areas` (area labels).
- `node scripts/profile.mjs --root .` prints `profile gap: <field>` for each missing, empty, TODO, wrongly typed or out-of-enum field (exit 1), warns on duplicate keys, and never guesses. `--json` prints the parsed block.

### Triage and track
- `node scripts/decide-triage.mjs --root . --base <ref> --branch <ref> [--lines sec=yes|no,door=yes|no,prod=yes|no] [--kind small|design|incident]`
- It lists `git diff --no-renames --name-only <base>...<branch>` (three dots: the branch's own changes; both paths of a rename), forces security yes when a path matches a profile glob, and prints the track, the per-role caps (`rules/tracks.json`, checked against the Track table) and the coder model (opus if any line is yes or the kind is incident). `--files a,b` triages planned paths before a branch exists. A line left unset is a `triage gap` (exit 2), even when a security glob forces security yes (the one-way-door question is separate); exit 64 is bad usage (an option-like ref is refused), 70 a git failure; `production_env: TODO` needs `prod=` on every run; an unfilled profile reports `profile gap`.

### Session ledger and audit
- Append events: `node scripts/ledger.mjs --ledger L.jsonl --session S <kind> key=value key:=<json> ...` (adds `ts` and `rule_version`). Replay: `node scripts/audit-ledger.mjs L.jsonl --profile .agents/project.md` prints violations by rule id (exit 1; also for an empty ledger or a profile gap).
- One JSON object per line; common fields `ts` (ISO 8601 with offset, non-decreasing per session), `session`, `rule_version`, `kind`. `topic` must equal the branch name: fix-round and re-review tracking join `triage`, `agent_start` and `review_start` on it, and the audit prints a non-fatal `warn:` line for a `review_start` whose branch has no `triage` topic.

The audit covers the `script` rules: reviews only on green CI of every recorded workflow and never on a red one, no second review of a sha without a fix, one fix-round review (role `re-reviewer`) per fix round on a new sha, security glob matches sticky, caps (delivery reviewers excluded), coder and reviewer models, merge only for a reviewed branch (or an owner waiver) with tree equality and green catch-up CI, base push alone, by the profile's pusher and only for a built merge, issue close after that push with `origin/<base>` equal to the merge sha; releases (OPR-09): a SemVer tag, annotated and pushed alone by its full ref by the profile's pusher (a `release_tool`'s own tags from CI excepted) on a commit pushed to the base (or a `release/X.Y` line), never moved; a release only from a pushed tag, with `--verify-tag` unless CI made it, made the way `release_via` says, `latest` only on the highest version, a pre-release marked as one, never re-created; TDD evidence, only for a topic whose `triage` recorded `tdd: true`: a review starts only after a `coder_report` with evidence `ok` since the last coder run (DEC-21, when that coder run is stamped with rules 1.7.0 or later), and a merge needs a `proof_check` on the reviewed head for every test in the `coder_report`'s `tests` (exempt tests need none; `not-checked` is a `warn:`) and no test whose `passes` was not cleared by a later `fails` (DEC-22); on a `tdd: true` topic a rules version going backwards is a LEDGER violation and mixed versions a `warn:`; a profile with `tdd: yes` and a triage (rules 1.7.0 or later) without `tdd: true` is a LEDGER violation; with `tdd: yes` or `auto` a rules version going backwards anywhere in the ledger is one; with `auto`, a triage that records `tdd: false` where `tdd-suggest` (from the triage files alone) says yes for a security path or one-way door is one, and `tdd: false` on a triage that touches production code is a `warn:`; an all-exempt coder report on a step that touches production code is a `warn:`; with `release_when: change-set` (and no `release_tool`), no merge is pushed while the previous one has no release (a last unreleased merge, or an unset `release_when`, is a `warn:`). Signing and the milestone-close timing are not in the ledger: `release-check --repo` reports signing, the worker's report the timing. Team and order (DEC-03 and kin): a yes triage line needs the full review or incident track; the incident coder runs on Opus; at `merge_built` the track's security and tech lead calls must have run, in order (analysts, engineers, design reviewers, security, tech lead last; incident: security first); a role outside the track roles, `coder` and `re-reviewer` is a LEDGER violation; the one-time rounds (`agent_start.extra`: `research`, `missing-fact`, `rebuttal`, `hypotheses`) run once per topic each and the rebuttal only on a one-way door, whatever the `cap_reason`; a `triage` records `trigger` (`asked` or `unasked` with `why`, from rules 1.11.0). Also: a second fix round after the re-reviewer ran needs an `owner_go` event (DEC-14); a `triage` with `files` must follow the last coder run before each review (DEC-02); `merge_built.catchup_sha` needs a green `ci_run` (DEC-05); a Sonnet re-reviewer needs the fix's `fix_scope: tests-docs` with no code path in its `files` (DEC-19); the `handoff` (one per direction per topic) and `intent` (`approved` after `checked`, `written` after `approved`) trail of `/decide` and `/intent`. `intent-plan.mjs` checks the plan's frontmatter, a `## Carried` section and, with `--approved`, `status: stable` and a human `verified`; `decision-lint.mjs` also needs the six sections and the `override tech lead:` and `override security:` lines.

The ledger is self-reported: it finds drift, it does not prove honesty.

### TDD evidence
- **Opt-in**: only when tdd is on: the profile's `tdd: yes`, or `tdd: auto` resolved yes for the step. With `auto`, `decide-triage.mjs` (with `--proof <test>` per proof test) runs `scripts/tdd-suggest.mjs`, deterministic and model-free: no `targeted_test` -> no (in a profile that is already a `targeted_test` gap); docs or config only -> no; no test file in the repo or the change -> no; production code touched with a security path or one-way door -> yes; production code touched and a proof test named -> yes; anything else -> no (unclear). `node scripts/tdd-suggest.mjs --root . --files a,b [--lines sec=..,door=..] [--proof <test>]...` prints the same answer and its reason (tests: `scripts/tdd-suggest.test.mjs`). The triage event records `tdd: true`, so the audit reads the setting from the ledger and stays reproducible; without it (unset or `no`) nothing below applies and a project audits exactly as in 0.14.0.
- Lines: a label, the exact test name, ` -- `, the text (the name ends at the first ` -- `; pytest ids, Go subtests and jest names with spaces or colons are fine, a name containing ` -- ` is not). Coder: `RED <test> -- <line>` (failing without the change), `GREEN <test> -- <line>` (passing with it), or `CANNOT FAIL FIRST <test> -- <reason>` (a reason about the test in at least three words: docs only, a pure refactor; a missing profile command is refused, it is a `targeted_test` profile gap), plus `TEST FIRST <test> -- <sha>` when the profile says `test_first_commit: yes`. Reviewer: `PROOF CHECK <test> -- fails | passes | not checked: <reason> | exempt`.
- `node scripts/proof-check.mjs --coder <report|-> [--test <name>]... [--file <changed path>]... [--root .] [--json]` checks a coder's report (DEC-21); with `--file`, an all-exempt report on a step that touches production code (by path, `scripts/paths.mjs`) prints a `proof warn:` line; `--json` prints `{required, exempt, gaps}` for the ledger. `--reviewer <answer|-> (--coder-report <report> | --test <name>...)` checks a reviewer's answer (either mode) (DEC-22): a result line for every test the coder's report proves (exempt tests need none, `exempt` is refused for a proved test), `not checked` with a reason, and a `passes` needs a CONFIRMED finding (any case) that says `proof does not prove` and names the test exactly (`TestA` does not match `TestAB` or `TestA/sub`). Exit 0 ok, 2 with `proof gap:` lines, 64 bad usage. It checks the lines are there, not that the output is real. Tests: `scripts/proof-check.test.mjs`.
- `node scripts/proof-revert.mjs --base <ref> --head <sha> --worktree <scratch> --keep <test file>...` prints, read-only, the commands that revert only the production part in the reviewer's scratch worktree: three-dot from the merge-base, modified and deleted files restored with `git checkout <merge-base> -- <file>`, added files removed, a rename's new path removed and old path restored (a kept renamed test stays as at head); a changed path with a newline is refused (exit 2, revert it by hand). Tests on a throwaway repo: `scripts/proof-revert.test.mjs`.
- `fails` means the test built, ran and failed; a build failure or anything else that kept it from running is `not checked: <reason>`. The reviewers create the scratch worktree with `git worktree add --detach` under `mktemp -d`, undo the revert with `git reset --hard` there and remove it with a plain `git worktree remove` (never `--force`; a refusal leaves it and reports its path).

### Golden scenarios
- `scenarios/<name>.json` is one scripted case, one file each (the plugin stays under claude.ai's 512-file limit): `description`, optional `profile` fixture name from `scripts/fixtures/` (default `real-profile`), `profile_extra` lines for the machine block such as `standing_waivers: [docs-only]`, optional `triage` input `{files, lines, kind}`, optional `report` `{role: coder|reviewer, tests}`, an optional `ledger` (the ledger's lines as strings, so a bad line stays bad) and `go_log` (the go log's lines), a `report_md` with `report` (and `coder_md`, the coder report a reviewer scenario derives its tests from), and `expect` (`track`, `caps`, `coder_model`, `triage_exit`, `gaps` for a triage; `report_exit`, `report_gaps` for a report; `violations` by rule id and `exit` for a ledger). `scripts/scenarios.test.mjs` runs them all in `npm test`.
- `node scripts/scenarios.mjs --list` names them, `--print <name>` shows the actual outcome (paste it into `expect.json` after reading it), and `[--run] [name]` compares and prints the difference.
- **Add one**: copy a close scenario, edit the ledger, run `--print`, check that every violation is the one you meant, save it as `expect.json`. A new `script` rule needs a scenario that expects its id (a test checks it).
- **Why they fail on purpose**: `scenarios/pin.json` holds the `/decide`, operator and rules versions the scenarios were reviewed against. An edit that changes behaviour fails its scenario; an edit that does not change it still needs a version bump (manifest), which fails the pin until the scenarios are re-read and the pin is updated. Scenarios use the anonymised fixture only; a test rejects project, host and user names.

### Ledger auto-capture
- `hooks/capture.mjs` (PostToolUse on `Bash`) appends `push` (`ref`, `sha`, `chained`, `by: agent`) for a successful `git push`, in a project whose main checkout has a profile (`.agents/project.md`), by `scripts/ledger.mjs`. The event goes to the main checkout's ledger even when the push ran in a worktree (`git -C <dir>` and `cd <dir> &&` are followed for the sha and the branch). The command is read the way a shell reads it, so a push inside a quoted string or heredoc records nothing; dry runs, deletes, tag pushes and a response that shows an error are skipped; the command line and remote are never recorded. It also appends `outward` for each shared or destructive action it saw run (class `go`, with the sha, for an unattended go's own action). Fail-open: any error means no event, never a blocked call. The owner's pushes are not seen, and `agent_start` stays a hand-appended event. Tests: `scripts/capture.test.mjs`.

### Condition ledger
- `condition` events (`topic`, `id`, `step`, `test`, `status` open or proved) track each condition of a security `conditions` verdict. `node scripts/condition-check.mjs [ledger] [--topic <branch>] [--json]` fails (exit 2, `condition gap:` lines) for a condition still open, or proved by a test that no `coder_report` of the topic lists (after the condition was opened) and no later `proof_check` shows failing without the change, or whose last `proof_check` passes; `--topic` with no condition of that topic also fails. The audit validates the event (`status`); the check is the merge-ready gate. Tests: `scripts/condition-check.test.mjs`.

### Decision-record lint
- `node scripts/decision-lint.mjs <record|-> [--json]` reads the step 8 table: the seven columns, a PM row, the verdict word for each call (security `accept|conditions|block`, PM and tech lead `adopt|reject <proposal>`, engineers and reviewers `for|against <proposal>`), a Conditions cell for `conditions`, no empty or placeholder cell, and, after the table, the three triage lines (`Security paths:`, `One-way door:`, `Touches real:`, exact labels at the start of a line) answered yes or no. Exit 2 with `decision gap:` lines, 64 bad usage. It checks the shape, not the judgment. Tests: `scripts/decision-lint.test.mjs`.

## Releases
Every project that sets `release_when` releases like a team with a release process: operator rule OPR-09, steps in [the merge protocol](skills/operator/refs/merge-protocol.md#releases), checked by the audit.
- **Version in the change.** SemVer, bumped with the change (or on a milestone's release branch) and reviewed with it, the changelog's `## X.Y.Z` section beside it; a `release_tool` (release-please, changesets, ...) owns that step when the profile names one.
- **Tag on the pushed merge.** Annotated (signed when a key is configured), on the merge commit once it is on the base with green CI, pushed alone by its full ref by the profile's `base_pusher`; never moved or deleted: a bad release is fixed forward and deprecated or yanked where it was published.
- **Release from the tag.** `release_via: ci`: a tag-triggered workflow tests, builds, writes `SHA256SUMS`, attests provenance and publishes (`templates/release.yml`, pinned action SHAs, least-privilege permissions). `session`: `gh release create --verify-tag` with the changelog section and the compare link. `--latest` only for the highest version, `--prerelease` for `-rc.N`.
- **`node scripts/release-check.mjs --next`** prints the last tag, the bump the commits since then need (Conventional Commits), the next version, and gaps: version files that disagree or do not cover the bump, a changelog behind, a tag that already exists; `--notes <file>` writes the release notes.
- **`node scripts/release-check.mjs --repo`** reads the forge's guard rails through `gh api` (required checks and no force push on the base, a tag ruleset on `v*`, immutable releases, CI, tag signing) and prints each gap with its fix for the owner. It changes nothing.

## Operator guard
`hooks/guard.mjs` runs before every Bash, Edit, Write, MultiEdit, NotebookEdit, Read, Grep, Glob, MCP, scheduler, message and skill call (MCP: Outward guard below; reads and schedulers: Unattended go) and denies a breach with the rule id and what to delegate. **A guardrail against slips, not a sandbox**: it reads the command the way a shell would for the common forms and fails closed on what it cannot read, but a determined session can still write a file in a way it does not model (for example a compiled program, or a tool it does not list). The permission system stays the real boundary.
- **Who is the operator**: the main thread of a session started with `claude --agent orbit:operator` (the hook input's `agent_type` is `orbit:operator` and it has no `agent_id`), or of a session started with `ORBIT_ROLE=operator claude`. A main checkout that only gets the SessionStart handoff is not detected: set `ORBIT_ROLE=operator` there. A subagent (hook input with `agent_id`) is never the operator, even when the variable is inherited.
- **OPR-01, files** (operator only): Edit, Write, MultiEdit and NotebookEdit are denied inside any git worktree of the repo (symlinks resolved), except `.agents/operator.md`; files outside the repo (a PR body in a temp dir) stay allowed.
- **OPR-01, git**: only read-only git runs (`status`, `log`, `diff`, `show`, `fetch`, `rev-parse`, `ls-remote`, `grep`, `worktree list`, `branch`, `tag`, `remote`, `stash` and `notes` listings, `config` reads, `reflog` views, ...). Each has an allowlist of known-safe options: any other option (`--upload-pack`, `--receive-pack`, `--exec`, `--output`, `grep -O`, an abbreviation such as `--outp`, a cluster such as `-nOecho`) is denied and named; so are `git -c`, a dynamic `-C` or argument, a `src:dst` refspec, and `git remote` with anything but `-v`, `show` or `get-url`. Every other subcommand is denied (`commit`, `merge`, `rebase`, `reset`, `checkout`, `switch`, branch changes, `worktree add|remove`, `cherry-pick`, `stash` changes, `tag` changes, ...). `push` runs only as a lone `git [-C <dir>] push origin HEAD:<base>` when the main checkout's profile has a `base_pusher` (`agent` or `owner`; the legacy `operator` reads as `agent` with a warning; a worktree's profile never grants it); without one, no push. Under the owner's unattended go the main thread also runs the go's two actions (Unattended go).
- **OPR-01, gh**: `gh pr merge|checkout` (wherever the flags sit), `gh api` writes (`-X PUT|POST|PATCH|DELETE`, or fields) on merges, pulls, refs, contents or git endpoints, any GraphQL call other than a read in the exact shapes below (Shared), any `gh api` call it does not read exactly (Shared), and any gh call run by `xargs` (any form, `-I` too), `find -exec|-execdir`, `fd -x|-X` or `parallel` are denied; reads, issues and comments stay allowed.
- **OPR-01, shell**: no write into a worktree of the repo (symlinks resolved) by a redirect, `tee`, `sed -i` or a `sed`/`awk` program that writes, `mv`, `cp`, `ln`, `install`, `rsync`, `rm`, `rmdir`, `unlink`, `shred`, `mkdir`, `touch`, `truncate`, `chmod`, `chown`, `patch`, `dd of=`, `curl -o|-O`, `tar x`, `find -delete|-exec <writer>`; no inline scripts (`python -c`, `node -e`, `perl -e|-i`, `ruby -e`) and no shell or wrapper whose command it cannot read (`bash script.sh`, a pipe or heredoc into a shell, `source`, `env -S`, `watch`, `script`, `flock`). Nested `$(...)`, backticks, `sh -c`, `eval`, `case` and functions are checked too. A write target that uses a variable set in the same command (an assignment, `export`/`declare` (also `-n`), `read`, `printf -v`, `for`, `mapfile`) is denied, except a path under a plain `$(mktemp)`, `$(mktemp -d)` or `$(mktemp [-d] -t NAME.XXXX)` (not `-p`, `--tmpdir` or a template path). `eval` shares the caller's directory and variables. A `cd` after `cd -`, or in a command with `||`, a pipe, a background `&`, a condition, loop, `case` or function, leaves the directory unknown. A command it cannot parse or resolve is denied (fail closed), and so is unreadable hook input with `ORBIT_ROLE=operator`, or a guard error in the operator session.
- **DEC-08** (every session, only with a profile whose `review_trailer` is set; the main checkout's profile sets it and the base, a worktree's profile can only add a trailer when the main one has none): a `git merge --no-ff` of a ref other than the base (`<base>`, `origin/<base>`, `FETCH_HEAD`, the base tip's SHA; the message never exempts it), also behind `git -c` or `git -C <dir>`, and a `git commit` that concludes a merge in progress, need a readable message with the `review_trailer` line in the last paragraph, with every `Co-Authored-By` line. No message, `--no-edit`, `--continue`, `-C|-c|--reuse-message`, a variable or a missing file are denied: pass `-F <file>`. Clustered flags (`-qm`, `-am`) are read.
- **Known limits** (out of scope, by design): interpreters running a script file (`python x.py`, `node x.mjs`, `make`, `npm run`), programs it does not list (compiled tools, editors), `find`/`xargs` forms beyond the listed writers, symlinks created in the same command or outside the repo that point into it, aliases and shell functions from the session, a variable or `$(...)` that expands to an option at run time in a non-git command, heredoc bodies with unquoted `$` expansions, and a worker's `git -C "$X"` with a dynamic directory, whose merge state is read from the session's own repo (a relative `-F` file there counts as unreadable).
- Other sessions see nothing from OPR-01. Without node the hook is silent (except with `ORBIT_ROLE=operator`, where it denies).

## Outward guard
The same hook classifies every `git`, `gh` and GitHub MCP call of every session (operator, peer, subagent) by what it does to the forge, after resolving wrappers (`env`, `sh -c`, `eval`, `xargs`, `command`, a path to git, `git-<sub>` programs, and any program with a git or gh word among its arguments: `find -exec`, `unbuffer`, `parallel`, `watch`, `flock`, ...; a data program such as `grep`, `cat` or `echo` is told by its own name only, and `find`/`fd` run only what follows their exec options), `git -C`, aliases (`git config --get alias.<name>` and `-c alias.*`) and `cd`. Threat model: [docs/threat-model.md](docs/threat-model.md).
- **Local** and **branch push** (a push to `origin` of a literal, non-protected branch): silent, as before.
- **Shared**: a push to a protected branch (`main`, `master`, `release/*`, the target of `origin/HEAD`, the profile's `base_branch` and `protected_branches`; the profile only adds) or to a target it cannot tell (bare `git push`, `git push <remote>`, another remote or a URL, `--repo`, a variable, a refspec with an unquoted `*`, `?`, `[`, `{` or extglob group, a non-literal `-C`, `--git-dir`, `--work-tree`, `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE`, `xargs`, a long option it cannot resolve by unique prefix, a destination under `remotes/`, `notes/`, `pull/`, `replace/` or `stash/`), a tag push (`--tags`, `--follow-tags`, `--all`, `refs/tags/`, `tags/`, a local tag name, `push.followTags` set), a remote branch delete, `gh release create|edit|upload`, `gh pr merge`, `gh run cancel|rerun`, `gh workflow run`, `gh auth token|login|refresh|setup-git`, `gh alias set`, `gh extension exec|install|upgrade`, `git remote add|set-url|set-head|set-branches|rename|remove` (where a push goes; `-v`, `show` and `get-url` stay silent), `gh repo edit|rename|sync`, `gh repo deploy-key add`, `gh pr review --approve`, `gh secret|variable set`, a `gh ruleset` change, `gh api` writes on `repos/{o}/{r}` and anything under it except issues, pull request create, edit and comments, and milestone and label create (`POST`) and edit (`PATCH`), on refs, git, releases, merges, contents, actions, branches or tags elsewhere, any `gh api` call it does not read exactly (a flag it does not know exactly, such as a clustered `-iX` or `-iq`; a control character other than newline and tab in an argument; an endpoint with `%`, `//`, `/./` or `/../`), any gh call run by `xargs` (any form, `-I` too), `find -exec|-execdir`, `fd -x|-X` or `parallel` (the wrapper appends or substitutes its arguments; a destructive one keeps its class), every GraphQL call (endpoint `graphql`, `/graphql`, a full URL or any case, or one a placeholder may make it) other than one in exact shapes, silent only when every argument is a separate `-f`/`-F`/`--field`/`--raw-field key=value` (no `@file`), `--jq`/`-q`, `--paginate`, `--silent` or `-H Accept…`, no argument holds a placeholder gh fills (`{owner}`, `{repo}`, `{branch}`, `:owner`, `:repo`, `:branch`), there is one `query` field, and it is a read (no `mutation` and no `#` anywhere in the query) or a mutation whose only top-level fields are the tracker's `updateIssueIssueType`, `createProjectV2`, `linkProjectV2ToRepository`, `addProjectV2ItemById` and `updateProjectV2ItemFieldValue` (clustered flags, `--input`, `-X`, `-R`, comments, fragments, aliases, a second operation or anything else stay shared), an `ln` or `cp -s|-l` outside these exact shapes: options from `-s -f -n -v -r -T` (`cp` also `-l`, clustered or not; no `-t` or `--target*`), operands without `..` or `.claude`, resolved against a known cwd, `git send-pack|http-push|receive-pack`, `git for-each-repo|filter-branch|difftool|mergetool`, an option whose value git runs (`--upload-pack`, `--receive-pack`, `--exec`, `clone`/`ls-remote -u`, `grep -O`, also by unique prefix; an argument it cannot read in `fetch`, `pull`, `clone`, `ls-remote`, `archive` or `grep`), `GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_ASKPASS`, `GIT_EDITOR`, `GIT_SEQUENCE_EDITOR`, `GIT_EXTERNAL_DIFF`, `GIT_PAGER` or `GIT_EXEC_PATH` set for git (a pager or editor `cat`, `less`, `true` or `:` stays silent), git or gh text with an outward word inside one argument of another program (`find -exec sh -c '…'`, `parallel ::: '…'`), a `claude` session, `tmux send-keys`, `screen -X stuff` or a write to `/dev/pts/*`, `git config` or `-c` of `alias.*`, the hooks path, `remote.*`, `url.*`, `push.*`, `include.path` or a key git runs as a command (pager, editor, `core.sshCommand`, textconv, filters, credential helper, ...; the values `cat`, `less`, `true` stay silent), `GIT_CONFIG_*` variables, an unknown git subcommand or gh command, and a parse error or guard error on text with git or gh and an outward word (also inside a script runner's own words, heredoc or a dynamic string; a script runner elsewhere in the call adds nothing). The hook answers **ask** under the permission modes that prompt (`default`, `acceptEdits`, `plan`, `auto`, `bypassPermissions`), so the owner approves it in the prompt; **deny** under `dontAsk` or a missing or unknown mode (headless `-p` runs stop there). A shared action that is not alone in its call (more than one command, a pipe, `||`, a condition) is denied: run it alone.
- **Destructive**: any force push (`-f`, `--force`, `--force-with-lease`, `--force-if-includes`, `+refspec`, `--mirror`, `--prune`, also on an own topic branch), deleting a tag, a protected branch or a target it cannot read (`push --delete $VAR`: name the branch literally), `gh api -X DELETE` (or a method it cannot read), `gh release delete|delete-asset`, `gh release upload --clobber`, `gh repo delete|archive`, `gh repo edit --visibility`, a `gh api` write to `repos/{o}/{r}` with `archived=true` (or a body it cannot read), a REST ref PATCH with `force=true`, GraphQL `deleteRef`, `deleteRepository`, `archiveRepository` or a forced `updateRef` (the name in any argument of a GraphQL call, whatever its shape), a forcing or deleting `send-pack`/`http-push` (`--force-with-lease` and `--force-if-includes` force), git or gh text inside one argument that shows a force or delete, a repo transfer, `gh repo sync --force`, `gh repo deploy-key delete`, `gh secret|variable delete`, `gh ruleset delete`, `gh run delete`, `gh project delete|item-delete|field-delete`, `gh issue delete`, `gh label delete`, a commit status or check run write (REST `statuses`, `check-runs`, `check-suites`, GraphQL `createCheckRun`, `updateCheckRun`, `createCheckSuite`; CI evidence), and GitHub MCP tools whose name holds `delete` or `force` (or with `force: true`): **deny** in every mode, decided before the profile is read. The owner runs it with `!` (the `!` path skips the hook).
- **GitHub MCP** (a server whose name holds `github`), fail-closed: tools named `get_*`, `list_*`, `search_*` or `read_*` are silent, every other one is shared; other MCP servers are untouched.
- **Operator**: every OPR-01 deny stays (under the unattended go its main thread may also run the go's two actions); what it ran before and now asks: the lone `git push origin HEAD:<base>`, `gh run rerun|cancel`, `gh workflow run`, `gh auth token`, and GitHub MCP writes (merge, push, ...).
- **`~/.claude`, every mode and session**: Edit, Write, MultiEdit, NotebookEdit and shell writes (redirects, the listed writers, a script or unparseable command that names it) into `~/.claude` (and `CLAUDE_CONFIG_DIR`: settings, plugins, transcripts, Orbit's go state and go log) are denied, also through a symlink whose target does not exist yet (followed, up to 40 hops; one it cannot resolve counts as `~/.claude`), and so is `ln` (any mode) or `cp -s|-l` naming a `~/.claude` path, and a glob (`*`, `?`, `[`, `{`) in an `ln`/`cp` operand or a write target that could match under `~/.claude` segment by segment (a relative pattern resolved against the cwd, `..` resolved; with an unknown cwd, any segment that could match `.claude`), except memory notes (`projects/<p>/memory/**.md`) and plan notes (`plans/*.md`); a scheduler, wakeup, trigger, loop, message, skill or MCP tool whose input holds `orbit:unattended` is denied. The glob matcher is an allowlist: it models `*`, `?`, a plain `[...]` set and comma braces exactly (a brace group with no comma is literal); a glob in another form (`[:`, `[=` or `[.` inside a set, `~` anywhere in it, a `{a..b}` sequence or `..` in a group with no comma, an unclosed `{`, an extglob group `+(`, `@(`, `!(`, `?(`, `*(`) is shared, and so is any glob on a line with `shopt`, `BASHOPTS` or a program the guard cannot read (also inside `sh -c` or `eval`); an extglob group holding `$`, a backtick, a quote or a backslash is a command it cannot parse; any other glob is silent (`rm *.log`, `sed -i s/a/b/ *.md`, also after `set -euo pipefail`).
- **Strict on doubt**: a helper git call (alias, tag, branch, `origin/HEAD`) that fails or runs out of its time budget (7 s for the whole hook run) gives the stricter class; a guard that times out or crashes blocks the call (`onFailure: block` in `hooks.json`). A claude.ai (portal) install does not store `onFailure` (its schema warns and drops it), so there only a hard crash or a timeout of the guard fails open; the guard's own errors still deny or share. The guard never reads the ledger; the capture hook records each shared or destructive action it saw run as an `outward` event, never as an authorisation.
- **Reason shape**: plain aligned text, a headline then only the rows that apply, values from parsed fields only (no URL, query, token or environment value):
  ```
  orbit · ASK · push to protected branch
  action   git push → origin/main
  commit   1a2b3c4 "first line of subject"
  by       subagent orbit:coder
  do       approve only if you gave the go
  ```
- **Not covered** (the permission system stays the boundary; see the threat model): git hook files (`.git/hooks`, `.githooks`) that push on commit, scripts and interpreters running a file (`node x.mjs`, `python x.py`, `bash x.sh`), `make` targets and `npm run`, `curl` or another HTTP client with a token, non-GitHub MCP servers, shell state persisting across calls (an `export`, a `GIT_*` variable or an alias from an earlier call), a `node` or `gh` shadowed on `PATH`, a program the agent runs that writes `~/.claude` (a compiled tool, a script file), and sessions where node is missing (the hook is then silent, except with `ORBIT_ROLE=operator`).

## Unattended go
For merges while the owner is away. Owner's bar (2026-10-17): green first-attempt CI plus the agent's review trailer; no person reviews a night merge before it lands. Command: `/orbit:unattended`; code: `hooks/unattended.mjs` (UserPromptSubmit) and `hooks/go.mjs`.
- **Open it, typed**: `/orbit:unattended on [8h|90m]` (default 12 h, at most 24 h). The prompt hook blocks the prompt and writes a one-time code to your terminal, never into the conversation: `/dev/tty`, else (Claude Code runs hooks without one, Linux) the first `/dev/pts/N` or `/dev/ttyN` of yours on stdin, stdout or stderr of its nearest 4 parent processes, opened through `/proc` and checked on the open fd (the terminal of the Claude Code that ran the hook, which an agent-launched Claude Code may own), never a pipe, file or the hook's output, which the agent could read; it keeps only the code's hash, for 2 minutes. Type `/orbit:unattended confirm <code>`; one wrong code clears it. A hand-back, scheduled prompt or cross-session message fires the same hook with no source field: it can ask for a code, and the guard denies the reads it parses while one is pending (below); a script file or compiled program the agent runs (a `tmux capture-pane` inside a script) can still read the terminal, a residual (Not covered). No terminal found (also macOS when `/dev/tty` fails): no code, no go. `off` and `status` work from any source.
- **While a code is pending**, every session's reads of `~/.claude` (transcripts included), pane captures and pty paths are denied.
- **Where it counts**: the session that opened it, its main thread (no `agent_id`), in `bypassPermissions` mode, until it ends; any missing field means no go (the attended behaviour).
- **What it allows**, alone in its call:
  - `git [-C <merge worktree>] push origin <40-hex merge sha>:refs/heads/<base>`, `<base>` both the target of `origin/HEAD` and the main checkout profile's `base_branch`, when: `origin`'s push URL (`pushurl`, `pushInsteadOf`) equals its fetch URL (`insteadOf` applied) on github.com, and every read below goes to that URL; the sha is a two-parent merge; its first parent is the remote base tip (`git ls-remote <url>`); its tree equals the second parent's; the main checkout profile's `review_trailer` (`Reviewed-by` only when it names none) is in its last paragraph with `Co-Authored-By`; it touches no `.github/**`, `.githooks/**`, `hooks/**`, Makefile, `*.mk`, `hooks.json` or `guard.mjs`, deletes no test file and adds no skip marker; the base tip has at least one green GitHub Actions run; the runs on the second parent are at least one, all completed, all success, all first attempt, and cover every workflow green on the base tip plus the profile's `required_checks`. Commit statuses and check runs are never read. The gh and git evidence calls share a 6 s deadline, each in its own process group killed at the deadline (a grandchild such as ssh cannot hold the hook); a timeout or error denies.
  - `git [-C <dir>] push origin --delete <topic>` for an unprotected branch whose remote tip is an ancestor of the remote base tip (same push URL and base checks).
- **Everything else**: every other shared action, a subagent's too, is denied with "needs the owner" (a base push in another form names the pinned one); destructive stays denied; `claude` sessions, `tmux send-keys`, `screen -X stuff` and `/dev/pts/*` writes are denied (attended: they ask). Tags and releases wait for the owner.
- **Night log**: the capture hook records each go action as an `outward` event of class `go`, with the sha pushed, and in `~/.claude/orbit/unattended/go-log.jsonl` (guard-protected); the audit counts a go base push (same session, sha, exit 0) as the owner's push for DEC-06 when `base_pusher` is `owner` only when the go log has the same record (default under the OS user's home, not `HOME`; `audit-ledger.mjs --go-log <file>` names another in the report's first line, `go-log: <file> (not default)`); a ledger line alone, which an agent can write, grants nothing.
- **Not covered**: the go state file and the go log can be forged by a program the agent runs, and such a program can read a pending code from the terminal (the go is intent; the evidence carries the safety); a night merge is proven by CI as the agent left it, not by a reviewer (the trailer is agent text; `scripts/**` and weakened tests outside these checks are residual); an empty commit pushed to get a first-attempt green shows in the night log.

## OKF docs
Optional docs automation for projects that keep docs as an [Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing) (OKF) v0.2 bundle (default `docs/okf`).
- `/orbit:okf-init` scaffolds the bundle (index, log, constitution, doc rules, a `roadmap/` folder with the milestones and the M1 plan, AGENTS.md/CLAUDE.md pointers, `.agents/okf.json`) and never overwrites.
- `node ~/orbit/scripts/validate-okf.mjs --root .` lints it against the OKF v0.2 spec (`type`, reserved `index.md` and `log.md`, the trust and provenance fields: `generated.by`, `verified` entries with `by` and `at`, `sources` entries with a `resource`, timestamps with a UTC offset) plus the stricter doc rules of skill `okf`; `warn:` lines (exit 0) flag an actor off the spec's convention, a human-verified `draft`, and an index line without the doc's description. Tests: `scripts/okf.test.mjs` (zero dependencies; settings from flags or `.agents/okf.json`; defaults: bundle `docs/okf`, 4000 chars per doc, AGENTS.md at most 80 lines, pointer files CLAUDE.md, GEMINI.md, .github/copilot-instructions.md, .cursor/rules/agents.mdc). Skill `okf` has the rules.
- `hooks/hooks.json` also runs the validator after Write/Edit under the bundle (silent without node or a bundle). `templates/githooks/pre-commit` is a commit-time snippet.

## Intent
The `intent` skill borrows one step from AWS's AI-DLC, Inception: a goal becomes small, approved units before anything is built. The rest of AI-DLC (mob rituals, 33 stages, an operations phase, gates at every stage) is not adopted: `/decide` and the operator already size the process to the risk.
- Triggers on its own when the owner states a goal that needs several sessions or branches (or run `/orbit:intent`); a goal that fits one session goes straight to `/decide`, and `/decide` hands a build that clearly exceeds one session back to `intent`.
- One question round, then a plan doc `roadmap/m<n>.md` in the OKF bundle: intent, exit tests, steps (`Step | Builds | Files | Proof | Depends | Hint`), carried issues. It is `stable` and `verified` by the owner once approved.
- `node ~/orbit/scripts/intent-plan.mjs --root . --plan <file|->` checks it before approval (zero dependencies, no model): the OKF per-doc rules (`scripts/okf-lib.mjs`, shared with validate-okf), the plan rules, sec=yes forced from the profile's `security_paths`, dispatch waves with no two steps touching the same paths, and the steps that go to `/decide` first. Exit 0 ok, 1 profile gap (`security_paths` only), 2 plan gap. Tests: `scripts/intent-plan.test.mjs`.
- Agents reused, none added: an optional light review by `designer` (reviewer role, on request), `/decide` only for a one-way-door goal, and the usual `/decide` per unit when it is built.

## Tracker
Orbit uses what the project's GitHub has, and adds nothing nobody reads (#14).
- `node ~/orbit/scripts/tracker.mjs [--detect]` detects with read-only `gh` calls under one 7 s deadline (a failure turns that feature off): a github.com origin, `gh` authed, the `project` scope, issues, labels, milestones, org issue types, Projects v2. Cached in `.orbit/tracker.json` of the main checkout (`checked_at`; `.orbit/.gitignore` ignores it), re-detected after 7 days or with `--detect`; prints one line of the features on. The SessionStart handoff runs `--cached`: it only reads the cache (no line without one) and starts `--detect` detached in the background when the cache is missing or stale, so the next session has it and the hook never waits for `gh`. The tracker's own writes (milestone and label create or edit, the issue type and Project mutations) are silent in the outward guard; their deletes are not.
- The profile wins: `issue_tracker: none`, `milestones: no`, `issue_types: no` turn theirs off; detection never turns on what the profile turns off.
- Issues the operator or `/orbit:intent` opens get a type label, an area label (profile `areas`), the release milestone and the issue type, whichever are on; one issue per finding round.
- GitHub Projects are optional, for large, complex work only: `github_projects: off` (default) or `on`. With `off`, `/orbit:intent` offers one in one line for a large plan; with `on` or the owner's yes, `tracker.mjs --plan "<milestone>" [--project]` prints the commands for one Project per intent milestone (repo linked, step issues added, a Board view grouped by Status: Todo, In progress, In review, Done, which the owner sets once). The operator moves items at dispatch and review. Never for a single change set; unavailable, skipped silently. Tests: `scripts/tracker.test.mjs` (gh stubbed).

## Agents sync
Instead of vendoring agent copies into `.claude/` (and keeping them in sync), install this plugin: the agents, command and skills load in every project. A project may still vendor its own copies in `.claude/agents`.
