# Changelog

## 0.15.0
- TDD evidence, two new `/decide` rules (`/decide` 1.4.0, operator 1.5.0, rules 1.7.0). DEC-21 `script`: the coder's report shows each proof test and each fix-round test red, then green, as labelled lines (`RED <test>:` failing without the change, `GREEN <test>:` passing with it, run with the profile's targeted-test command), or `CANNOT FAIL FIRST <test>: <reason>` (docs only, a pure refactor). DEC-22 `script`: the `reviewer` and `re-reviewer` run each such test alone in a scratch worktree with only the production part of the diff reverted (never the coder's branch, nothing heavier than that one targeted test; their one exception to read-only) and write `PROOF CHECK <test>: fails|passes|not checked`; a pass is a CONFIRMED finding, "proof does not prove", and blocks the merge; no targeted-test command in the profile is `not checked`.
- `scripts/proof-check.mjs` (no model, zero dependencies): `--coder` and `--reviewer` check those lines (exit 2 with `proof gap:` lines). Ledger kinds `coder_report` (`evidence` ok or gap) and `proof_check` (`result`); the audit checks DEC-21 (a review needs evidence ok since the last coder run) and DEC-22 (a merge needs a proof check on the reviewed head and no test whose latest check passes) on events stamped with rules 1.7.0 or later, so older ledgers audit as before. Scenarios take a `report` (`report.md`, run through proof-check); ten new scenarios. Tests: `scripts/proof-check.test.mjs`, audit and profile tests.
- Optional profile field `test_first_commit` (`no` default, or `yes`: the coder commits the failing test alone before the fix and reports `TEST FIRST <test>: <sha>`); existing profiles stay valid, triage ignores it. The profile template names the targeted single-package run as the targeted-test command.
- `commands/decide.md` stays under the size limit: step 2's triage command moved verbatim to `refs/decide/team-tracks.md`, which already held the rest of step 2.

## 0.14.0
- Releases as a team does them, for every project (operator 1.4.1, rule OPR-09 `script`; `/decide` 1.3.3 points its delivery to it). The profile says when (`release_when`: `change-set`, `milestone`, `never`; setting it is the owner's standing go), how (`release_via`: `ci` or `session`), which tool owns versions (`release_tool`), and the `changelog` and `version_files`. The version is bumped in the change and reviewed with it; the tag is annotated (signed when a key is configured), on the merge commit once it is on the base, pushed alone by the base pusher and never moved; the release comes from the tag, by a tag-triggered workflow or `gh release create --verify-tag`, `--latest` only for the highest version. Fixes on an older line go on `release/X.Y`. The release steps in `skills/operator/refs/merge-protocol.md` are rewritten to match.
- `scripts/release-check.mjs` (read-only, no dependencies): `--next` derives the bump from Conventional Commits since the last tag, checks the version files and the changelog agree with it and the tag is new, and writes the notes with the compare link; `--repo` reads the GitHub guard rails (required checks, no force push, a `v*` tag ruleset, immutable releases, CI, tag signing) and prints each gap with the owner's fix. Tests: `scripts/release-check.test.mjs`.
- `templates/release.yml`: a tag-triggered release workflow, offered and written only on the owner's go. A `build` job with a read-only token checks the tag is annotated and on the default branch (or a `release/X.Y` line), tests, builds, writes `SHA256SUMS` and the notes; a separate `release` job, which runs no project code, holds the write and OIDC permissions, attests provenance and publishes, `--latest` only for the highest version. Action SHAs pinned.
- Ledger kinds `tag_push` and `release`, `merge_built.release_skip`; the audit checks OPR-09 (six new scenarios). Triage ignores the release fields. Rules 1.6.1.

## 0.13.0
- Intent skill 1.0.0 (`skills/intent`), AI-DLC's Inception step and nothing else of AI-DLC: a goal too big for one session becomes a milestone plan of small units before any build. It triggers on its own (or `/orbit:intent`), sends a one-session goal to `/decide`, asks one question round, drafts `roadmap/m<n>.md` as an OKF v0.2 doc (intent, exit tests, steps with Files, Proof, Depends and a provisional Hint, carried issues), checks it, and asks the owner once; the approved plan is `stable` with the owner in `verified`. A one-way-door goal goes through `/decide` first; units are built through the usual `/decide` and operator flow. No new agents: an optional `designer` light review on request. In an operator session the writes are one docs-only worker task.
- `scripts/intent-plan.mjs` (no model, zero dependencies) checks a rendered plan from a file or stdin before approval: the OKF per-doc rules, an Intent section, Steps and Exit tests by column name, placeholders, Files shape, unknown or cyclic Depends, the Hint grammar (prod when the profile names a production_env), sec=yes forced from `security_paths` (exact for paths, "may touch" by literal prefix for directories and wildcards), dispatch waves with no two steps touching the same paths, and the steps that go to `/decide` first. Only a `security_paths` gap stops it. Tests: `scripts/intent-plan.test.mjs`.
- `scripts/okf-lib.mjs`: validate-okf's per-doc checks, now shared with intent-plan; validate-okf keeps the bundle checks (links, indexes, reserved files, AGENTS.md) and its behaviour.
- OKF scaffold: the M1 plan has an `## Intent` section and the new Steps columns; every template's actor is `process:orbit-okf-init`. Skill `okf` 1.0.3 and the doc-rules template: a plan is written when planned or started, and a change to an approved plan's intent, steps or exit tests needs a new approval appended to `verified`. Rules 1.5.0.
- Review fixes (intent 1.0.1, rules 1.5.1): the overlap check is conservative and never misses: an exact file is matched by the glob itself, and a directory or wildcard entry meets a security path when their segments agree up to the shorter one or the glob's first `**` (plain-name and `*` globs cover what lies below them); placeholders in Files and exit tests are gaps; Files split on commas, semicolons, `<br>` and spaces; an escaped `\|` stays in its cell, `## Steps (track A)` and CRLF files are read; `production_env: TODO` makes `prod=` optional with a warning; a footnote without a definition no longer crashes the shared OKF checks. Repo `CLAUDE.md`: every versioned merge is tagged and released.
- Re-review fix (rules 1.5.2): a second `## Steps` or `## Exit tests` section in one doc is a gap (one per doc; split by track into separate docs) instead of being dropped; `.` and `..` segments in Files are gaps; a plain name that is a directory on disk counts as a directory.

## 0.12.3
- Operator guard (`hooks/guard.mjs`, PreToolUse on Bash and the edit tools): OPR-01 and DEC-08 are enforced by a hook instead of prose. In the operator session (`claude --agent orbit:operator`, or `ORBIT_ROLE=operator`; never a subagent) it denies edits other than `.agents/operator.md`, write git commands, pushes other than the lone base push when the profile names a `base_pusher`, `gh pr merge|checkout` and shell writes into the repo's worktrees; it fails closed on what it cannot parse. In every session with a `review_trailer` profile it denies a `--no-ff` merge message (and the commit that concludes such a merge) without the trailer in the last paragraph with `Co-Authored-By`. `rules/rules.json` 1.4.0: `hook` rules carry `enforced_by` (tested); OPR-01 also names `reset`, `checkout`, `switch`, `stash` and branch changes. Operator skill 1.3.0. Tests: `scripts/guard.test.mjs`.
- Guard review fixes (rules 1.4.1): read-only git refuses options that run a program or write (`--upload-pack`, `--exec`, `--output`, `grep -O`, `src:dst` fetch refspecs) and `config` writes; variables assigned in the command make a write target unknown (a `mktemp` directory stays allowed); `cd -` makes the directory unknown; shells with a script, stdin or `--`, `source`, `env -S`, `watch`, `script`, `flock` fail closed, `setsid`, `chronic`, `ionice` and `builtin` are unwrapped; gh merges, API ref/content writes and GraphQL mutations are denied; DEC-08 also denies a `--no-ff` merge or merge-concluding commit without a readable message (`--no-edit`, `--continue`, reuse) and reads clustered `-qm`/`-am`; catch-up merges by `FETCH_HEAD` or the base SHA pass; Edit/Write outside the repo is allowed; `case`, functions, `stash list|show`, `notes show` parse; more writers (`patch`, `rsync`, `dd`, `curl -o`, `tar x`, `unlink`, `shred`, `chmod`, `chown`, `find -delete|-exec`, inline `python|node|perl|ruby`, writing `sed`/`awk` programs); write targets resolve symlinks; the README says it is a guardrail, not a sandbox.
- Guard last review round (rules 1.4.2): read-only git takes only a per-subcommand allowlist of options (abbreviations and clusters such as `--outp`, `-nOecho`, `-qu<cmd>` are denied and named), `git remote` only `-v`, `show`, `get-url`; the `mktemp` exception only for a plain `mktemp [-d] [-t NAME]`; `eval` shares the caller's state; a `cd` under `||`, a pipe, `&` or a condition leaves the directory unknown; `printf -v` and `declare -n` assign; GraphQL queries from `@file` or `--input` are denied; DEC-08 exempts catch-up merges by ref only (no message prefix) and parses `git -c` and `git -C <dir>` before the subcommand; README lists the known limits.
- Guard re-review fix (rules 1.4.3): `--format` is no longer read as taking the next argument (git takes it only as `--format=`, so `git log --format --output=<file>` slipped through), nor shortlog's `--committer`; the separate-value options were checked against real git; the `printf -v` test uses a variable from the environment, so it fails when the check is removed; a test covers a worker's `git -C "$X" commit` during a merge.

## 0.11.0
- Fresh worker per task: the operator starts a new worker for every task and resumes one only to finish its own open branch (fix round, catch-up, merge build, cleanup, review findings), because a resumed worker re-reads its whole context each message and its cost grows. Delivered workers are retired. The profile's `Worker reuse: fresh-per-task / resume-ok` field (default `fresh-per-task`) controls it; `resume-ok` restores the old behaviour.

## 0.10.0
- Optional pull requests per project: the profile's `Pull requests: yes` makes the coder open a PR after the push, reviewers start on a PR only after CI is green on its head SHA, the operator posts each review summary as a PR comment and uses its id in the review trailer. Default and fallback is the issue-comment flow (`no`); the merge is the verified local `--no-ff` merge in both modes, never the GitHub merge button.
- Profile templates carry the new `Pull requests` field.
