# Session ledger fields

Detail of the `/decide` command (`commands/decide.md`, Ledger) and the operator skill. Load when you append a ledger event or read an audit violation.

One JSON object per line; `ts`, `session` and `rule_version` are stamped by `scripts/ledger.mjs`; `topic` equals the branch name. Append: `node "${CLAUDE_PLUGIN_ROOT}/scripts/ledger.mjs" --session <id> <kind> key=value key:=<json>` (`key:=` for booleans, numbers, arrays).

| kind | fields |
|---|---|
| `triage` | `topic`, `sec`, `door`, `prod`, `track`, `files` (changed paths), `tdd` (`true` or `false` as `decide-triage.mjs` prints it: the profile's `tdd: yes`, or `auto` resolved for the step; sticky once true; unset is false), `trigger` (`asked` or `unasked`; `unasked` needs `why`, the one line of the started-unasked rule; required from rules 1.11.0) |
| `agent_start` | `role` (for a `reviewer` in fix-round mode, brief starts `Mode: fix-round`, the role is `re-reviewer` here and on `review_start`, so DEC-14 and DEC-19 apply), `model`, `topic`; `resumed` (a resumed worker keeps its model), `worker` (an id for the worker session: a later coder event with the same id and another model is a violation even without `resumed`; a fresh coder gets a new id), `reason` (`ci-failed-twice` needs opus); `phase` (`design`, `build`, `fix`, `delivery`; a reviewer defaults to `delivery` once a `ci_run` with that `branch` exists); `fix_scope` (`tests-docs` or `code`), `files` (a fix coder's changed paths: `tests-docs` with a code path is a violation); `extra` (`research`, `missing-fact`, `rebuttal` or `hypotheses`: a one-time round outside the caps, once per topic each, never excused by a `cap_reason`; `rebuttal` is the same tech lead and only on a triage with `door: yes`); `cap_reason`, or `outside_cap` (excludes the call from the caps; needs a `cap_reason`). A `role` other than the track roles, `coder` and `re-reviewer` is a violation |
| `ci_run` | `branch` (= topic; a run without it counts for no topic's phase default), `sha`, `workflow` (default `default`), `state` (`green`, `red`, `pending`) or `conclusion` (`success`, `failure`, ...); the latest run per workflow counts |
| `review_start` | `branch`, `sha`, `ci_state`, `role` (`reviewer`, or `re-reviewer` for the reviewer in fix-round mode) |
| `merge_built` | `branch` (required), `merge_sha`, `tree_equal`, `ci_state` (of the catch-up merge), `catchup_sha` (the head of the catch-up merge; needs a green `ci_run` in the ledger; required from rules 1.11.0), `waived` (a `standing_waivers` class of the profile, or `owner` with `waiver_reason`), `release_skip` (why this merge is not released, OPR-09) |
| `push` | `ref` (`main`, `HEAD:main`, `origin/main`, `refs/heads/main` all mean the base), `sha`, `chained`, `by` (`agent` or `owner`) |
| `issue_close` | `n`, `origin_base_sha`, `merge_sha` |
| `tag_push` | `tag` (`vX.Y.Z`), `ref` (`refs/tags/vX.Y.Z`, the full ref it was pushed by), `sha` (the merge commit), `by` (`agent` or `owner`; `ci` when a `release_tool` tags), `annotated`, `chained`, `signed` |
| `release` | `tag`, `url`, `via` (`session` default, or `ci`), `verify_tag`, `latest`, `prerelease` |
| `coder_report` | `branch`, `evidence` (`ok` or `gap`, the exit of `proof-check.mjs --coder`), `tests` (its `--json` `required`: the RED/GREEN tests, `[]` when none), `exempt` (the CANNOT FAIL FIRST ones), `sha` |
| `proof_check` | `branch`, `sha` (the reviewed head), `test`, `result` (`fails`, `passes`, `not-checked`, `exempt`) |
| `condition` | `topic`, `id`, `step`, `test` (the proof test name), `status` (`open` or `proved`) |
| `owner_go` | `topic`, `why`: the owner's go to a further fix round after the re-reviewer ran (DEC-14: a second `phase: fix` coder run needs it) |
| `handoff` | `topic`, `from`, `to` (`decide`, `intent` or `operator`): at most one per direction per topic, then stop and report. Appended by whoever hands over |
| `intent` | `milestone`, `phase` (`questions`, `draft`, `checked`, `approved`, `written`): the `/intent` trail, appended with `scripts/ledger.mjs` as each step ends; `approved` needs an earlier `checked` (the plan script passed), `written` an earlier `approved` |

`coder_report`: after every coder run, before its review (DEC-21). `proof_check`: one per `PROOF CHECK` line of a reviewer, also in fix-round mode (DEC-22); every test in the report's `tests` needs one on the reviewed head, and a `passes` blocks the merge until a later `fails` of that test. Both apply only to a topic whose `triage` recorded `tdd: true`, so the audit reads the setting from the ledger. Cross-check with the profile: when it says `tdd: yes`, a `triage` stamped with rules 1.7.0 or later without `tdd: true` is a LEDGER violation (older triage events predate the field); when it says `tdd: auto`, such a triage without `tdd: true` or `false` is one too, and so is `tdd: false` where `tdd-suggest.mjs` on the triage files (tests present only if they include one; the repo is not read) says yes for a security path or one-way door; `tdd: false` on a triage that touches production code warns. With the profile's `tdd: yes` or `auto`, a rules version going backwards anywhere in the ledger is a LEDGER violation. An all-exempt `coder_report` on a topic whose triage files include production code is a `warn:`. DEC-21 applies when the coder run is stamped with rules 1.7.0 or later, DEC-22's coverage when the `coder_report` is; on a `tdd: true` topic a rules version going backwards is a LEDGER violation and mixed versions a `warn:`; a topic without it audits as in 0.14.0.

`condition`: the latest event per `topic` and `id` counts; one `open` event per condition of a security `conditions` verdict, appended when the verdict is recorded; a `proved` event for the same `id` once its test is proved. Before the merge is reported ready, `node "${CLAUDE_PLUGIN_ROOT}/scripts/condition-check.mjs" --topic <branch>` fails (exit 2, `condition gap:` lines) for a condition still `open`, or `proved` with a test that is in no `coder_report` `tests` of the topic and no `proof_check` that `fails`, or whose last `proof_check` `passes`. The audit only validates the event.

Auto-capture: the plugin's PostToolUse hook (`hooks/capture.mjs`, in a project whose main checkout has a profile) appends `push` by itself for a successful agent `git push` (`ref`, `sha`, `chained`, `by: agent`), to the main checkout's ledger even when the push ran in a worktree (`git -C <dir>` and `cd <dir> &&` are followed). Skipped: dry runs, deletes, tag pushes (also a bare tag name), `--all`, `--mirror`, `--repo`, and anything inside a quoted string or heredoc. `agent_start` is not captured (the hook sees the call after it ended and from the wrong checkout): append it by hand, and `push` by hand only for a push the hook cannot see, such as the owner's (`by: owner`).

Replay: `node "${CLAUDE_PLUGIN_ROOT}/scripts/audit-ledger.mjs"` (the profile's `ledger_path`; it prints violations by rule id, `warn:` lines are not fatal).

Team and order checks (DEC-03 and its kin), per topic from the `triage`: a yes line needs the full review or incident track; at `merge_built` the track's security and tech lead minimums (`rules/tracks.json`) must have run (rounds with `extra` and delivery reviewers do not count); calls run analysts, engineers, design reviewers, security, tech lead last, and on an incident security before the engineers and reviewers; the incident coder runs on Opus. DEC-02: a `triage` with `files` must follow the last coder run before every `review_start` (re-run `decide-triage.mjs --branch` after each coder run and append it). DEC-05: `catchup_sha` must have a green `ci_run`. DEC-19: a Sonnet re-reviewer needs the fix coder's `fix_scope: tests-docs`.
