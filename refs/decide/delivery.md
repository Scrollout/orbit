# Act and delivery

Detail of the `/decide` command (`commands/decide.md`); the numbered rules and the flow live there. Load when delegating a build and delivering it (steps 9-10): coder models, review, issues, merge, fix round.

9. **Act.** Update the docs with the decision (a decision record when it is new, in the profile's format and location), write the failing test or check first, and implement. Delegate a decided build step with a clear spec to `coder` on a new worktree branch (the profile's convention), passing the conditions and the `proof` test; commit there only. With an operator session, every write (docs, decision record, failing test, implementation) goes to a worker; the PM writes nothing in the repo. Merge as step 10 says, the base pushed by whoever the profile's "who pushes the base" names; deploy stays with the owner unless the profile says otherwise.
10. **Delivery** (rules from the profile; where it is silent, use the defaults below):
   - Split a step expected over about 1,000 changed lines (generated files aside) into steps that each pass the profile's full check.
   - `coder` runs on Sonnet. Override its model to `opus` when any triage line is "yes" for the first build and for a fix round that changes a security path's behaviour; and once, for a re-run, when CI fails twice on its step. A fix round that changes only tests or docs stays on Sonnet.
   - `re-reviewer`: pass `model: sonnet` when the fix round changes only tests or docs; otherwise its default.
   - Caps: a call beyond the track's cap needs its reason written in the brief before it runs, and in **Cost**.
   - Test: follow the profile's CI policy. When CI is the only full run, the coder runs only the targeted checks the profile names, never the full run or the heavy suites locally, pushes so CI runs and reports without waiting; you watch CI and start no local full run (with an operator session, push requests go through it). A failure gets a `test` issue and goes back to the same coder to fix at its root cause, then the tests run again; never rerun or fix it yourself, and never send a branch with a failed run to review.
   - Review: none only when the profile's waiver holder (the owner) waived it, per branch or for a class such as docs-only steps or small routine steps (under about 150 changed non-test lines, every triage line "no"). Otherwise, once the pushed branch has its first green CI run, a fresh `reviewer` with the brief, `<base>..<branch>` and the coder's report; only its findings enter your context.
   - Issues: every finding, red run and carried item is an issue in the profile's tracker, opened by you with at least one type label from the profile's label set and the issue type the profile maps it to (when the tracker has types); the coder's brief lists the numbers, its commits say `Fixes #n` only when they fully close the issue, otherwise `Refs #n`; you close each when its fix merges into the base branch.
   - Triage of findings: CONFIRMED findings and PLAUSIBLE security findings go back to the coder; style is logged, not applied; a finding against the spec or design is a new question for this protocol.
   - Merge (CI green on the branch), per the profile's merge rules: merge the base branch into the topic branch and push it, CI on that merge commit replacing a local full check; once every triggered run is green, a worker builds the merge in a fresh detached worktree from `origin/<base>` (`git worktree add --detach ../<repo>-merge-<topic> origin/<base>`) with `--no-ff` and the profile's review trailer on that merge commit, in the same last paragraph as `Co-Authored-By` (the reviewer that ran, e.g. `reviewer (opus)`, and the step; never a session name; `<owner> waived - <reason>` only for a branch whose review the owner waived), and checks the merged tree is the branch's green tree (`git rev-parse HEAD^{tree} <branch>^{tree}`; if the base moved, merge it into the branch again first). The base is pushed alone, never chained after the merge, by whoever the profile's "who pushes the base" names (`owner`: hand the owner the exact `! git -C <merge worktree> push origin HEAD:<base>`). Then `git fetch origin` and confirm `origin/<base>` equals the merge SHA before closing issues; a worker then removes the worktrees and deletes the branch locally and on the remote.
   - Fix: resume the same `coder` with the kept findings (failing test first). After the fix's first green CI run, a fresh `re-reviewer` checks only the fixed findings, once, with the kept findings, the coder's report and `<base>..<branch>` of the fix. Still open after that: stop and show the owner both positions.
