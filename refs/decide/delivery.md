# Act and delivery

Detail of the `/decide` command (`commands/decide.md`); the numbered rules and the flow live there. Load when delivering a build (step 10; step 9 is in the core): coder models, review, issues, merge, fix round.

10. **Delivery** (rules from the profile; where it is silent, use the defaults below):
   - Split a step expected over about 1,000 changed lines (generated files aside) into steps that each pass the profile's full check.
   - Coder model: DEC-04. In short: Sonnet by default; Opus when any triage line is yes (first build and every code fix round) and for one re-run after CI failed twice on its step; a tests-or-docs-only fix round may stay on Sonnet. A resumed worker keeps its model, so to change it start a fresh `coder` on the same branch with the kept findings.
   - `re-reviewer`: DEC-19 (Sonnet only when the fix round changes only tests or docs).
   - Caps: a call beyond the track's cap needs its reason written in the brief before it runs, and in **Cost**.
   - Test: follow the profile's CI policy. When CI is the only full run, the coder runs only the targeted checks the profile names, never the full run or the heavy suites locally, pushes so CI runs and reports without waiting; you watch CI and start no local full run (with an operator session, push requests go through it). A failure gets a `test` issue and goes to a coder to fix at its root cause (DEC-16), then the tests run again; never rerun or fix it yourself.
   - Review: waivers per DEC-15; a class such as docs-only steps or small routine steps (under about 150 changed non-test lines, every triage line "no") must be named in the profile's `standing_waivers`. Otherwise, once the pushed branch has its first green CI run (DEC-01), a fresh `reviewer` with the brief, `<base>...<branch>` and the coder's report; only its findings enter your context.
   - Issues: DEC-17. You open them (type label from the profile's label set, the issue type the profile maps it to when the tracker has types); the coder's brief lists the numbers; you close each when its fix merges into the base branch (DEC-07).
   - Merge, per the profile's merge rules, in this order: (1) the review on the branch's first green CI run, and the fix round; (2) at merge time the catch-up merge of the base into the topic branch, pushed, CI green on that merge commit (it replaces a local full check; repeat if the base moves); (3) only then a worker builds the `--no-ff` merge in a fresh detached worktree from `origin/<base>` (`git worktree add --detach ../<repo>-merge-<topic> origin/<base>`) with the profile's review trailer on the merge commit, in the same last paragraph as `Co-Authored-By` (DEC-08: the reviewer that ran, e.g. `reviewer (opus)`, the branch head it reviewed, never a session name; `<owner> waived - <reason>` only for a waived review), and checks the merged tree is the branch tree (`git rev-parse HEAD^{tree} <branch>^{tree}`). The base is pushed alone, never chained after the merge, by whoever the profile's "who pushes the base" names (`owner`: hand the owner the exact `! git -C <merge worktree> push origin HEAD:<base>`). Then `git fetch origin` and confirm `origin/<base>` equals the merge SHA before closing issues; a worker then removes the worktrees and deletes the branch locally and on the remote.
   - Fix: the same `coder` takes the kept findings (failing test first; DEC-18 says which findings), resumed only to finish its own branch and keeping its model (DEC-04). After the fix's first green CI run, a fresh `re-reviewer` checks only the fixed findings, once (DEC-14), with the kept findings, the coder's report and `<base>...<branch>` of the fix.
